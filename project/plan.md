# План разработки · 26 ноября 2026

Проверяющий открывает главную, создаёт аккаунт, проходит проверку через Sumsub WebSDK в личном кабинете и видит мем с котиком на главной. После выхода и повторного входа результат сохраняется. Второй пользователь получает доступ только после собственной успешной проверки.

Работаем по одному этапу. Перед реализацией каждого этапа сначала составляем подробный черновик, обсуждаем существенные решения и получаем явное согласование пользователя. Без согласованного подробного плана реализацию не начинаем. Перед началом сверяем ближайшую задачу в [state.md](state.md), после выполнения записываем туда фактический результат и способ его повторить. Причины выбора стека — в [decisions.md](decisions.md), документация провайдера — в [sumsub.md](sumsub.md).

## 1. Инициализация и локальный каркас

Задача следующего агента. Инициализировать локальный Git-репозиторий в текущем каталоге, сохранив инструкции и проектные заметки. Добавить в .gitignore локальные секреты и файлы SQLite. Go module размещается в app/go.mod, будущий код приложения — в app/. Добавить точку входа в app/cmd/server. Выбрать поддерживаемую версию Go для проекта и согласовать её с будущей сборкой контейнера.

Один HTTP-сервер на net/http отдаёт HTML через html/template. Главная страница находится на /, кабинет на /account, проверка работоспособности на /healthz. На этом этапе достаточно перехода между страницами. На Mac уже обнаружены Go 1.24.5, Git, sqlite3 и Homebrew. Для запуска каркаса требуется только Go.

**Приёмка.** Из каталога app/ команда `go run ./cmd/server` запускает сервер. В браузере открываются обе страницы на localhost:8080, запрос к /healthz получает HTTP 200. Записать проверенные команды в README.

## 2. Регистрация, сессия и кабинет

[Подробный план этапа 2](stages/02-registration.md) — **выполнен 26 ноября 2026**.

Подключить SQLite через database/sql и modernc.org/sqlite. Локально хранить базу в файле, путь задавать конфигурацией. Создавать схему при запуске на пустой базе. Хранить идентификатор пользователя, логин, хеш пароля, состояние проверки и серверные сессии. Идентификатор сессии передавать в HttpOnly cookie, на HTTPS использовать Secure.

В кабинете гость может зарегистрироваться или войти. Вошедшему пользователю показать статус и выход. Новый аккаунт начинает со статуса «Проверка не начата».

**Приёмка.** Зарегистрироваться, выйти, войти снова и перезапустить сервер. Аккаунт и статус сохраняются. Повторная регистрация с тем же логином не создаёт второго пользователя.

## 3. Доступ к котику

[Подробный план этапа 3](stages/03-meme.md) — **черновик, ожидает согласования**.

Главная предлагает гостю зарегистрироваться, а вошедшему пользователю с незавершённой проверкой — перейти в кабинет. После одобрения главная выводит изображение с GET /meme. Обработчик самостоятельно проверяет текущую сессию и статус в базе. Картинку хранить вне публичной статики и отдавать с Cache-Control: private, no-store.

**Приёмка.** В тесте создать двух пользователей, задать одному одобренный статус и обратиться к одному URL с разными сессиями. Изображение получает только одобренный пользователь. Проверить также гостевой запрос и запрос после выхода. Для этого этапа достаточно тестовых данных в локальной базе.

## 4. Первый деплой на Fly.io

Установить CLI через `brew install flyctl` и войти через `fly auth login`. Подготовить Dockerfile и fly.toml. Сервер слушает 0.0.0.0:8080, internal_port соответствует порту сервера. Использовать одну Fly Machine и один Fly Volume в том же регионе, смонтировать том в /data, базу разместить в /data/app.db. До создания оплачиваемых ресурсов сверить выбранную конфигурацию и стоимость. Публичный HTTPS-адрес понадобится для входящих webhook.

**Приёмка.** По публичному адресу открыть главную, создать аккаунт, повторно развернуть приложение и войти с прежними данными. Проверить /healthz. Записать воспроизводимые команды деплоя в README.

## 5. Запуск Sumsub WebSDK в кабинете

К этому этапу нужно подтвердить, какой Sandbox разрешён для проекта, и проверить название и шаги доступного Individual verification level. Подготовить Sandbox App Token и Secret Key как серверные секреты. При нажатии «Подтвердить личность» backend берёт стабильный ID пользователя из серверной сессии и подписывает запрос к Sumsub на выдачу краткоживущего SDK access token для выбранного уровня.

JavaScript в кабинете подключает WebSDK с официального CDN, запускает виджет с полученным токеном и при истечении срока запрашивает новый для того же пользователя. Тестовые документы передаются через виджет.

**Приёмка.** Войти в тестовый аккаунт, открыть виджет и пройти настроенные шаги с тестовыми материалами. Проверить обновление SDK-токена. До получения серверного решения доступ к /meme остаётся закрыт.

## 6. Сохранение результата и обновление интерфейса

Подключить Sandbox webhook к публичному HTTPS-маршруту. Проверить подпись по исходному телу запроса до обработки события. Сопоставить externalUserId с локальным аккаунтом. При applicantReviewed сохранить результат. GREEN открывает мем, RED с RETRY приглашает повторить нужный шаг, RED с FINAL показывает отказ. В процессе проверки кабинет показывает ожидание. После завершения виджета интерфейс запрашивает актуальный статус у нашего backend.

**Приёмка.** На тестовых событиях проверить одобрение, повторную подачу, окончательный отказ, неверную подпись и повторную доставку. Убедиться, что устаревшее событие не перезаписывает более свежий результат. Затем получить настоящий Sandbox webhook в развёрнутом приложении и проверить статус после обновления страницы.
