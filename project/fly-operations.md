# Управление тестовым демо на Fly.io

Команды выполняет ассистент по запросу пользователя. Merge в main сам по себе ничего не публикует. Цель — приложение `sumsub-cat-demo` в организации `personal`, регион `iad`, одна Machine shared-cpu-1x 512 МБ и один том `app_data` 1 ГБ с SQLite. Команды ниже выполняются из `app/`.

Перед операцией выполнить `fly auth whoami` и `fly apps list`, сверить имя и владельца. Для существующего приложения проверить `fly status -a sumsub-cat-demo` и `fly volumes list -a sumsub-cat-demo`. Использовать текущие ID, сверить регион и привязку тома. Ошибка авторизации или сети не доказывает отсутствие ресурса. При неожиданном составе ресурсов сначала выяснить причину.

## «Задеплой новую версию для теста»

1. По умолчанию взять свежий origin/main после git fetch. Если пользователь указал ветку или коммит, взять указанную версию. Записать SHA и собирать из чистого checkout этого коммита (при локальных правках использовать отдельный worktree). Проверить изменения, включая совместимость с существующей БД. До миграции с риском потери данных подготовить восстановление и согласовать последствия.
2. Выполнить подходящие тесты изменённой функции, для Go — `go test -race ./...` и `go vet ./...`. Сверить fly.toml с целевым приложением, томом и настройками HTTPS. Проверить `fly config validate -a sumsub-cat-demo`.
3. Для существующего приложения использовать прежний том. Если приложение было полностью удалено и пользователь снова просит деплой, сверить актуальные условия Billing, создать приложение командой `fly apps create sumsub-cat-demo --org personal`, проверить список томов и создать один `fly volumes create app_data --size 1 --region iad --app sumsub-cat-demo`. Новый том означает пустую БД. При изменении тарифа, необходимости карты или дополнительных ресурсов согласовать выбор с пользователем.
4. Выполнить `fly deploy --remote-only --ha=false -a sumsub-cat-demo`. Конфигурация из Git возвращает обычный autostart после ручной паузы. Проверить релиз через `fly releases -a sumsub-cat-demo`, одну Machine с passing check, нужный том, HTTPS /healthz (200) и пользовательский сценарий изменённой функции. Для обновления с сохранением базы проверить вход с прежним тестовым аккаунтом, если доступен. При сбое проверить status, checks и logs прежде чем повторять действие.
5. Сообщить опубликованный SHA, результат проверок, ссылку и короткие шаги для теста. Обновить фактическое состояние в state.md, без секретов или данных аккаунтов.

## «Останови» или «выключи без удаления хранилища»

По умолчанию сохранить SQLite. Обычный autostop удобен между посещениями, но запрос к сайту будит машину. Для паузы до явного возобновления применить временную настройку непосредственно к Machine. Подставить её текущий ID вместо MACHINE_ID.

```sh
fly machine update MACHINE_ID -a sumsub-cat-demo --autostart=false --skip-start
fly machine stop MACHINE_ID -a sumsub-cat-demo
fly machine status MACHINE_ID -a sumsub-cat-demo --display-config
fly volumes list -a sumsub-cat-demo
```

Если машина уже остановлена, после обновления настройки достаточно проверки. Подтвердить состояние stopped, отключённый autostart в конфигурации сервиса и наличие того же тома. Вычисления остановлены, учёт хранения тома и корневого диска продолжается. Для возобновления той же версии вернуть `fly machine update MACHINE_ID -a sumsub-cat-demo --autostart=true`, при состоянии stopped выполнить `fly machine start MACHINE_ID -a sumsub-cat-demo` и проверить /healthz.

## «Выключи полностью» или «удали вместе с хранилищем»

Для этого демо такая формулировка означает удалить приложение, машину и том. Облачные аккаунты, статусы и сессии SQLite будут потеряны. Код и конфигурация остаются в Git. Если пользователь просит сохранить базу, до удаления сделать согласованную проверенную копию вне Fly. Если смысл команды неоднозначен, сохранить данные.

После сверки цели выполнить `fly apps destroy sumsub-cat-demo` и подтвердить удаление именно этого приложения. Проверить успешный ответ Fly и отсутствие приложения в `fly apps list` личной организации. Если оно уже отсутствует, достаточно проверки. Сообщить результат и обновить state.md и сведения о доступности в README. Уже начисленное потребление останется в Usage/Billing. Эти действия относятся только к ресурсам указанного приложения.
