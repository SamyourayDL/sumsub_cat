## Результат и границы

После отправки материалов пользователь видит ожидание. Подписанное уведомление Sumsub
изменяет статус в SQLite. Одобрение открывает мем, RETRY предлагает исправить материалы,
FINAL показывает отказ. Результат сохраняется после обновления, повторного входа и
перезапуска. Другой аккаунт не получает чужой статус или доступ к мему.

Этап 5 уже дал WebSDK, серверную выдачу токенов и стабильный externalUserId. Полный
ручной прогон этапа 5 не является условием начала кода этапа 6: его приёмка переносится
в блок Б этого плана. На 26 ноября пользователь осмотрел кабинет, но не нажимал кнопку
верификации; настоящие ключи запросом к API и виджет ещё не проверены.

Две независимые отметки результата: «основной код написан / локальные проверки пройдены»
и «Sandbox-приёмка пройдена». Весь этап становится «Выполнен» после блока Б.

Вне объёма: Production, KYB, workflows, новые уровни для бизнес-сценариев,
административная панель, произвольное ручное одобрение через публичный API,
хранение документов, полноценная очередь событий и мониторинг промышленного сервиса.
Этап 7 остаётся финальной репетицией сдачи и проверкой README на чистом окружении.

## А. Основной код

### А1. Технологии и конфигурация

Сохраняем Go/net/http, database/sql + SQLite, html/template и обычный JavaScript.
Для HMAC используем crypto/hmac и crypto/sha256, для данных — encoding/json.
Новых runtime-зависимостей, очереди, WebSocket или frontend-сборки не требуется.

Добавляем серверную переменную SUMSUB_WEBHOOK_SECRET — отдельный секрет webhook,
не SUMSUB_SECRET_KEY для API. При её отсутствии endpoint отвечает 503 и не принимает
события; приложение можно запустить для локального осмотра. Перед настоящей приёмкой
секрет обязателен. Значения не выводим в ошибках, логах, HTML или README.

### А2. Приём и проверка webhook

Предлагаемый маршрут: POST /webhooks/sumsub. Он не требует пользовательской cookie:
это запрос Sumsub к нашему серверу. Исключение из CrossOriginProtection делаем только
для точного webhook-маршрута; остальные POST сохраняют существующую защиту.

- Ограничиваем тело (64 КиБ), читаем исходные байты до JSON-разбора.
- Принимаем только HMAC_SHA256_HEX в X-Payload-Digest-Alg; Dashboard настраиваем
  на этот алгоритм. X-Payload-Digest проверяем через hmac.Equal после hex-декодирования.
  Отсутствующие, неоднозначные или неподдерживаемые заголовки не принимаем.
- После подписи разбираем событие. Для изменения статуса обязательны sandboxMode=true,
  индивидуальный applicant, ожидаемый levelName, известный externalUserId и валидное
  время события. Если applicantId уже связан с аккаунтом, другой ID не принимаем.
- testMode=true из кнопки тестовой отправки Webhook manager подтверждаем без изменения
  пользовательского статуса: проверка соединения не должна выдавать доступ к мему.
- Подписанные события другого уровня, неизвестного пользователя и неподдерживаемого
  типа подтверждаем 200 без изменений. Это существенно для общего корпоративного
  Sandbox: наши маршруты обрабатывают только аккаунты нашего демо.
- Неверная подпись — 403; повреждённый JSON/обязательные поля — 400; большой body — 413;
  ошибка записи БД — 500. Успешно записанное/повторное/устаревшее событие — 200.
- Успех возвращаем только после commit. В обработчике нет внешних сетевых запросов.
  Логи содержат технический исход обработки, без сырых тел, документов, комментариев,
  токенов или секретов.

### А3. Состояния и связь с аккаунтом

Используем существующий users.verification_status; добавляем миграцию schema v2 → v3
для минимальных метаданных: applicantId, время последнего принятого события UTC
с миллисекундами, отпечаток нормализованных значимых полей и признак конфликта.
Не сохраняем сырой webhook, clientComment или сведения из документов.

| Источник | Состояние приложения | Поведение кабинета |
| --- | --- | --- |
| Новый аккаунт | not_started | «Проверка не начата», кнопка запуска |
| applicantCreated | in_progress | «Продолжите проверку», возможность открыть SDK |
| applicantPending | pending | «Материалы отправлены, ожидаем результат» |
| applicantOnHold | on_hold | «Проверка требует дополнительного рассмотрения» |
| applicantReviewed / GREEN | approved | «Личность подтверждена», ссылка на главную с мемом |
| applicantReviewed / RED + RETRY | retry | «Нужно исправить материалы», повторное открытие того же applicant |
| applicantReviewed / RED + FINAL | rejected | «Проверка отклонена», без предложения повторной подачи |
| applicantReset | not_started | Отозвать прежний допуск, предложить пройти проверку заново |

Выдача SDK-токена сама по себе не означает отправку материалов. Временное сообщение
«Материалы отправлены, ожидаем результат» допустимо после SDK-события, но оно не меняет
сохранённый результат и не даёт доступа к мему. Детали исправления документов показывает
SDK; на первом этапе в кабинете достаточно наших фиксированных русских сообщений.

### А4. Повторы и порядок событий

Сопоставление по сохранённому externalUserId, проверка метаданных и обновление статуса
выполняются атомарно. Нельзя создавать локального пользователя из webhook.

Основное время — createdAtMs (UTC). Для старого формата createdAt допустим разбор
с секундной точностью; ограничения одинаковых времён обрабатываются явно.
Событие старше сохранённого игнорируется. Повтор с тем же временем и теми же значимыми
данными ничего не меняет. Более новое событие может менять результат, в том числе
отзывать approved: статусы не считаем необратимой лестницей.

При одинаковом времени и конфликтующих значимых результатах порядок неизвестен.
Предлагается безопасное поведение: отметить конфликт, закрыть доступ к мему и показать
«Статус проверки уточняется». Новый непротиворечивый более поздний webhook снимает
конфликт. Для демо это фиксируем как ограничение; автоматическую сверку через отдельный
Sumsub API пока не добавляем. Ручная диагностика — по Dashboard и повторной отправке
актуального события. Это наше проектное правило, а не гарантия порядка от Sumsub.

### А5. Статус в кабинете и доступ к мему

Добавляем GET /account/verification/status: действующая сессия и существующая привязка
страницы обязательны, ответ Cache-Control: no-store. Возвращаем только собственное
состояние и допустимое действие; идентификатор пользователя из query не принимаем.

HTML сразу отображает сохранённый статус. JavaScript обновляет его после событий SDK,
при возвращении фокуса и примерно раз в 5 секунд во время активной проверки/ожидания.
Параллельных опросов нет; в скрытой вкладке опрос приостанавливается. После terminal
результата регулярный опрос останавливается; ошибки сети не подменяют статус отказом.
При 401/409 закрываем старый виджет и предлагаем открыть кабинет заново, как в этапе 5.

Для RETRY используем прежний externalUserId и текущий механизм токенов. Для approved
и FINAL кнопка повторной подачи не предлагается. Серверный маршрут токенов проверяет
состояние, чтобы UI не был единственным ограничением. Обновление токена уже открытого
виджета в незавершённом сценарии не должно случайно ломаться.

Главная и /meme продолжают проверять свежий серверный статус. При конфликте или любом
состоянии, кроме approved, доступа нет. Уже показанную/скачанную картинку отозвать нельзя;
запрещается следующий запрос. Автоматический переход на главную не нужен: показываем
явную ссылку «Посмотреть котика».

### А6. Последовательность реализации и передача кода

1. Миграция и атомарное применение нормализованного события.
2. Проверка подписи, разбор webhook и точный маршрут без пользовательской сессии.
3. Status endpoint и серверные правила доступных действий.
4. Русские состояния кабинета, polling и повторный запуск после RETRY.
5. Конфигурация, README, state.md и описание ограничений.

Существующие тесты и gofmt/build помогают контролировать реализацию по ходу работы;
полный набор новых сценариев и их приёмка выделены ниже. После блока А можно показать
готовый diff, но кодовый PR нельзя сливать до локальных проверок Б1. Настоящий Sandbox
и деплой не обязательны для merge локально проверенного кода.

## Б. Постобработка — тестирование и настоящая интеграционная приёмка

Этот блок выполняется после основного кода. Он включает отложенные проверки этапа 5.
Сбой здесь может потребовать исправления кода и повторения затронутых проверок.

### Б1. Локальные тесты без настоящего Sumsub — до merge кода

Добавить/расширить Go httptest + временные SQLite и Node node:test с имитациями
DOM/fetch/SDK. Настоящие ключи, документы и пользовательскую базу не использовать.

Матрица: корректная/неверная подпись и изменённые байты тела; отсутствующий/неверный
алгоритм; лимит тела; повреждённые поля; неизвестный пользователь/level; Production
событие; testMode; все состояния таблицы; повтор, обратный порядок, равное время с
конфликтом и последующее восстановление; конкурентная доставка; ошибка БД и повтор;
миграция с сохранением аккаунтов/сессий; перезапуск и повторный вход; изоляция двух
аккаунтов; 401/409 status API; RETRY; polling/пауза/ошибка сети; отсутствие доступа к
мему без approved и после отзыва. Событие SDK не должно одобрять пользователя.

Команды из app/: go test -race -timeout 180s ./..., go vet ./...,
go build -o bin/server ./cmd/server, node --test tests/*.test.mjs; git diff --check.
Проверить Docker-сборку после запуска Docker daemon (в этапе 5 он был выключен).
Просмотреть полный diff и отсутствие секретов; если CI появится — дождаться обязательных
проверок. После этого один законченный кодовый PR можно squash merge в main.

### Б2. Подготовка внешней среды — отдельное действие после кода

Fly App ранее удалено. По отдельному запросу восстановить демо и том по
[инструкции эксплуатации](../fly-operations.md), передать ключи через серверные secrets.
Настроить отдельный Sandbox webhook на HTTPS /webhooks/sumsub, порт 443, без redirect;
выбрать HMAC_SHA256_HEX и перечисленные в А3 события. Существующие чужие webhooks не менять.

Sumsub требует быстрое соединение и ответ; проверить поведение холодного старта Fly.
На время приёмки при необходимости держать Machine запущенной, не меняя постоянный
режим и расходы без запроса. Локальный localhost не принимает внешние webhooks.

Тестовая отправка из Webhook manager проверяет адрес/подпись/доступность, но её testMode
не должна менять аккаунт. Это отдельная проверка от симуляции решения applicant.

### Б3. Настоящий webhook с искусственно заданным решением

Использовать официальный Sandbox-only метод:
POST /resources/applicants/{applicantId}/status/testCompleted.
Он позволяет задать GREEN, RED+RETRY или RED+FINAL, после чего сам Sumsub отправляет
applicantReviewed. Это реальная доставка провайдером с искусственным решением,
а не локально поддельный webhook и не прохождение экранов SDK.

Для каждого основного исхода — отдельный тестовый аккаунт/applicant. Сначала открыть
SDK для создания applicant; если нужно проверить доставку до камерного шага, этот
метод позволяет отделить тест результата от полного прохождения виджета.
applicantId берём из Dashboard; не угадываем по локальному ID.

В постобработке подготовить небольшой служебный инструмент подписанного запроса
(или воспроизводимую команду) с ключами из окружения. В рабочем приложении не добавлять
маршрута «одобрить себя». Для RED передать подходящие rejectLabels и reviewRejectType.
Проверить три исхода, повторную доставку, сохранение после обновления/входа/перезапуска
и независимость второго аккаунта. Проверить логи доставки в Dashboard.

### Б4. Настоящие экраны WebSDK и тестовые документы

Использовать официальные Verification document templates, сохраняя исходные файлы
и имена. Раздельно пройти Accepted, Resubmission request и Final rejection.
Для RETRY проверить замену документа и продолжение того же applicant. Проверить
получение/обновление SDK-токена и поведение при выходе/смене аккаунта.

Presets Sandbox управляют результатами проверок, а экраны задаёт verification level.
Manual review удобно использовать для контролируемого ожидания; автоматические
Approve/Reject/Skip задают тестовые результаты. Конкретный preset выбирается для
конкретного прогона: не смешивать ожидание автоматического решения с Manual review.

Текущий id-and-liveness содержит Advanced liveness. Skip/Approve не убирают экран
камеры. До прогона выбрать с пользователем один вариант:
- пройти текущий уровень человеком с камерой (изображение лица уйдёт в Sandbox);
- создать отдельный разрешённый document-only уровень для тестов без лица, а реальную
  liveness-приёмку оставить явно незавершённой.

Реальные паспорта не нужны. Возможность полностью искусственного прохождения текущего
Advanced liveness не подтверждена. Не менять общий корпоративный уровень ради теста:
его настройки могут отражаться в Production. Материалы/изображения не сохранять в Git.

### Б5. Завершение и фиксация результата

Записать по каждому сценарию: способ (локальная имитация / testCompleted / настоящий SDK),
ожидание, фактический результат, дату и оставшиеся ограничения — без персональных
материалов и секретов. Обновить state.md, sumsub.md и README.

Этап 5 закрыть только после фактической проверки выбранного полного уровня и обновления
токена. Этап 6 закрыть после локальных проверок и настоящей цепочки Sumsub → webhook →
SQLite → кабинет → мем. Если liveness отложен, явно оставить соответствующую часть
приёмки незавершённой. Затем этап 7 — чистый браузер, README и репетиция сдачи.
