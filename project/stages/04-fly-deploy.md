# Этап 4. Ранний деплой на Fly.io

**Статус: Черновик — ожидает согласования.** Подготовлен 26 ноября 2026 по просьбе пользователя перейти к этапу 4 и объяснить первый деплой. Одобрение этапа 3 не является согласованием этого плана. Реализация и создание ресурсов не начаты.

## Результат и границы

Публичный HTTPS-адрес приложения: гость регистрируется, входит и видит собственный статус; после повторного деплоя аккаунт, статус и сессия сохраняются. /healthz отвечает 200. Доступ к /meme остаётся защищённым. Ноутбук пользователя не нужен для работы опубликованного приложения.

Включены упаковка приложения, базовое ограничение злоупотреблений перед публичным запуском, конфигурация Fly.io, один сервер и постоянный том, первый и повторный деплой, документация эксплуатации. Sumsub, webhook, собственный домен, CI/CD, несколько регионов и репликация не входят. Публичного одобрения пользователя не добавляем.

## Кто что делает

Ассистент после согласования готовит код, Dockerfile, .dockerignore, fly.toml, тесты и PR; помогает разбирать ошибки и проверяет результат. Пользователь регистрируется и входит в Fly.io, сам вводит платёжные данные, выбирает допустимые расходы. По текущему запросу команды, создающие облачные ресурсы и публикующие приложение, выполняет пользователь по инструкции. Ассистент не создаёт их за него без отдельного поручения.

## Предлагаемая конфигурация

- Один Fly App, одна Machine shared-cpu-1x с 512 МБ RAM и один Volume 1 ГБ в одном регионе. Предпочтительно европейский регион; точный код, наличие ресурсов и цену сверить в аккаунте перед созданием. Размер памяти проверить под тестовой нагрузкой; увеличение требует сверки стоимости.
- Отключить создание запасных Machines: --ha=false. Несколько независимых SQLite не дадут общей базы.
- Публичный адрес <app-name>.fly.dev, без покупки домена, выделенного IPv4, Postgres и дополнительных сервисов. HTTPS на Fly Proxy, internal_port=8080, force_https=true, COOKIE_SECURE=true.
- Volume app_data монтируется в /data; DB_PATH=/data/app.db. Новая облачная тестовая база: локальные базы, сессии и персональные данные не загружать. Миграция схемы выполняется при старте существующим кодом, не через release_command.
- MEME_PATH=/app/resources/meme.jpg. Общий тестовый мем копируется в образ отдельным файлом. Постоянная смена этого файла на хостинге — через новый образ и деплой; ручная замена в корневой файловой системе не считается постоянной. Локальная замена без перезапуска сохраняется. Пользовательских загрузок пока нет.
- Для редких тестов: auto_stop_machines="stop", auto_start_machines=true, min_machines_running=0. Первый запрос после простоя может быть медленнее. Перед интеграцией webhook и демонстрацией пересмотреть необходимость постоянно работающей машины и стоимость.
- Одна Machine допускает краткий простой при деплое/сбое. Volume сохраняет данные при обычном обновлении, но не заменяет резервное копирование. Проверить включённые snapshots; не выдавать их за полноценную стратегию восстановления важных данных.

## Технологии и безопасность

Многоэтапный Dockerfile: сборка Linux-бинарника на закреплённой Go 1.27.4, минимальное runtime-окружение с CA-сертификатами для будущих HTTPS-запросов. Перед выбором base image проверить наличие тега; не менять Go молча. Согласовать права непривилегированного процесса на смонтированный /data и проверить их в контейнере. Runtime не должен содержать исходные секреты или локальную базу.

.dockerignore исключает .env, секреты, SQLite и sidecar-файлы, data/uploads, логи, bin и лишние файлы из контекста сборки. Это отдельная защита от отправки файлов remote builder: одного .gitignore недостаточно. Сборка на Fly возможна удалённо; Docker Desktop нужен только для локальной контейнерной проверки, не обязателен для самого remote deploy. Новых Go-зависимостей по умолчанию не требуется.

До публикации добавить ограничение POST /login и /register до bcrypt: лимит по адресу клиента и нормализованному логину, общий предел параллельных дорогих операций без неограниченной очереди. Начальные значения для демо: 10 попыток за минуту на адрес, 10 за 15 минут на логин, не более двух одновременно выполняемых операций; превышение — 429 с понятным сообщением и Retry-After. Это предложения данного плана, не текущая функциональность. Хранилище лимитов ограничено по размеру и очищает старые записи; после перезапуска лимиты сбрасываются. Не вводить постоянную блокировку аккаунта.

Локально адрес берётся из RemoteAddr; в Fly-режиме доверять заголовку адреса только по проверенному контракту Fly Proxy и явной настройке, не произвольному X-Forwarded-For. Проверить границу доверия и подмену заголовков до реализации. Существующие CSRF, лимит тела, cookie и no-store сохраняются. Не логировать пароли, сессии, токены или тела форм. В этом этапе Sumsub-секреты ещё не нужны.

## Последовательность

1. Согласовать этот план. Без согласования — только объяснения и исследование.
2. Ассистент готовит и проверяет защиту входа и контейнер, конфигурацию с документированными параметрами и README. Один завершённый PR на подготовку приложения к деплою; без создания ресурсов. Если локальный Docker daemon недоступен, сообщить это и отдельно провести проверку образа доступным способом до публикации.
3. Пользователь создаёт личный аккаунт Fly.io, проверяет Billing, устанавливает CLI через brew install flyctl, выполняет fly auth login и fly auth whoami. Не передаёт в чат токены и платёжные данные.
4. Ассистент и пользователь сверяют имя приложения, организацию, регион, ресурсы, текущий тариф и оценку расходов. Предложение бюджетного ориентира — до $5/месяц для демо, не гарантия и не технический лимит списаний. Создание платных ресурсов — только после явного выбора пользователя.
5. После подготовки файлов пользователь выполняет из app/ fly launch --no-deploy --ha=false --no-db --no-redis --no-object-storage --no-github-workflow. Не соглашаться на замену подготовленного Dockerfile без проверки. Выбрать согласованные имя, организацию и регион. --no-deploy создаёт/настраивает приложение, но не означает отсутствие любых облачных изменений; не выполнять этот шаг заранее.
6. Проверить получившийся fly.toml. Затем создать том: fly volumes create app_data --size 1 --region <region> --app <app-name>. Placeholder заменить согласованным значением. Не создавать второй том, если первый уже создан: сначала fly volumes list.
7. Выполнить fly deploy --remote-only --ha=false. Проверить fly status, fly checks list, fly volumes list и fly logs. Сверить одну Machine, один том и HTTPS. Если deploy завершился ошибкой — сначала диагностика, не повторное создание ресурсов.
8. Пройти пользовательский сценарий ниже. Повторить deploy той же командой и проверить сохранность аккаунта/сессии/статуса.
9. Зафиксировать фактические команды, адрес, стоимость выбранной конфигурации, ограничения и результат в README/state; конфигурационные изменения — через PR. Подробный план пометить выполненным только после удалённой приёмки.

## Критерии проверки

- go test -race ./..., go vet ./..., go build; git diff --check. Тесты лимитов, восстановления после окна, подмены заголовков, конкуренции и ограниченного размера хранилища.
- Контейнер стартует, слушает 0.0.0.0:8080, читает JPEG и пишет только в выделенный каталог БД. Безопасный контекст сборки; сохранение базы при замене контейнера с тем же томом.
- HTTPS /healthz — 200, HTTP перенаправляется на HTTPS, cookie содержит Secure/HttpOnly/SameSite. Гость и второй пользователь не получают чужой доступ к мему.
- Создать тестовый аккаунт, проверить собственный статус, перезапустить/повторно развернуть приложение, обновить страницу, выйти и войти снова: данные и действующая сессия до выхода сохраняются.
- Превышение лимита даёт 429, а не бесконтрольный bcrypt; после окончания окна можно войти. Проверить память/ошибки сервера в пределах выбранной Machine.
- Нет непреднамеренных дополнительных Machines, томов, баз или оплачиваемых сервисов. Публичная ссылка записана в README. Локальные проверки и фактические облачные проверки перечислены отдельно.
