**Статус: Согласован.** Версия 1 подтверждена пользователем 26 ноября 2026 сообщением «План подтверждаю». Принят весь описанный объём, технологии, правила и проверки. Реализация ещё не начата; текущий запрос пользователя — объяснить сессии и защиту форм.

## Проверяемый результат и границы

Гость создаёт аккаунт с логином и паролем, попадает в кабинет со статусом «Проверка не начата», выходит и входит снова. После перезапуска сервера аккаунт, статус и непросроченная сессия сохраняются в SQLite. Другой пользователь видит только собственный кабинет.

В этот этап входят формы, хранение пользователей, паролей и сессий, базовая защита запросов, тесты и документация. Sumsub, изменение статуса через SDK/webhook, выдача мема и деплой остаются следующими этапами. Не добавляем восстановление пароля, email, OAuth, роли и отдельный frontend. Это локальный учебный сценарий; защиту публичного входа от перебора и нагрузочные ограничения нужно включить в подробный план до публичного деплоя.

## Технологии и причины

| Область | Предложение | Почему |
| --- | --- | --- |
| Go | Текущий Go 1.27.4 | Уже проверен каркас; глобальную установку на Mac этот этап не меняет. |
| HTTP и HTML | net/http, html/template и go:embed | Остаётся обычная отдача HTML с сервера; формы отправляют POST без обязательного JavaScript. |
| Данные | database/sql + modernc.org/sqlite | Уже выбранная в общем плане файловая SQLite; драйвер не требует CGo. SQL пишем явно, ORM не нужен. |
| Пароли | golang.org/x/crypto/bcrypt, cost 12 | Готовые операции хеширования и сравнения, соль и параметры находятся в результате. Ограничение — максимум 72 байта пароля; проверяем его до хеширования и сообщаем пользователю. |
| Сессии | SQLite + crypto/rand + SHA-256 | Непрозрачный случайный токен в cookie, его хеш и срок жизни в БД; сервер может немедленно отозвать сессию. JWT и Redis не нужны. |
| CSRF | http.CrossOriginProtection + SameSite cookie | Защита изменяющих запросов от чужого origin без дополнительной зависимости; изменения только через POST. |
| Тесты | testing, httptest, временная файловая SQLite | Проверяем настоящий HTTP-сценарий и сохранение данных после повторного открытия БД. |

Новые прямые зависимости — modernc.org/sqlite и golang.org/x/crypto; конкретные совместимые стабильные версии проверим при реализации и сохраним в go.mod/go.sum. Самопроизвольное обновление Go ради зависимости не входит в план: при несовместимости сначала пересмотрим выбор.

**Роутер.** Предлагаю оставить net/http. Знакомый пользователю chi подходит для групп маршрутов и middleware, но на этом этапе не меняет пользовательский результат и не даёт существенного выигрыша. Отдельного выбора между роутерами для утверждения плана не требуется; если пользователь предпочитает chi, изменим этот пункт до реализации.

## Пользовательский сценарий и правила ввода

На GET /account гость видит две явно разделённые формы: «Регистрация» и «Вход». После регистрации автоматически создаётся сессия и выполняется redirect в кабинет. Вошедшему пользователю показываются логин, текущий статус из БД (для нового аккаунта — «Проверка не начата»), ссылка на главную и кнопка «Выйти».

Предлагаемые правила: логин из 3–32 латинских букв, цифр, дефиса или подчёркивания; крайние пробелы убираем, регистр приводим к нижнему. Alice и alice — один логин. Пароль — минимум 12 символов, максимум 72 байта UTF-8; его не обрезаем и не нормализуем. Подсказки видны рядом с полями, пароль при ошибке не возвращается в HTML. Только вымышленные тестовые учётные данные.

При повторной регистрации показываем «Этот логин уже занят». Для неверного пароля и неизвестного логина одинаковое сообщение «Неверный логин или пароль»; выполняем сравнение с фиктивным хешем и для неизвестного логина. Ошибки БД не маскируем под неверный пароль и не раскрываем пользователю SQL.

## Хранение и конфигурация

Создать таблицы users и sessions и первую версию схемы в транзакции. Версию схемы хранить через PRAGMA user_version; повторный запуск не пересоздаёт данные, неизвестная более новая версия вызывает понятную ошибку запуска.

- users: стабильный внутренний ID, уникальный нормализованный логин, password_hash, verification_status (начальное значение not_started), created_at. ID не зависит от логина и впоследствии станет основой externalUserId для Sumsub.
- sessions: уникальный token_hash, user_id с внешним ключом, created_at и expires_at. Исходный токен в БД не сохраняется.

DB_PATH задаётся окружением, по умолчанию data/app.db относительно рабочего каталога app/. При отсутствии каталога приложение создаёт его с ограниченными правами. Для одного экземпляра достаточно одного открытого соединения к SQLite, включённых foreign_keys и busy_timeout. Создание аккаунта и сессии атомарно; уникальность логина обеспечивает ограничение БД, включая параллельные запросы. Файл БД и его служебные файлы уже исключены из Git.

COOKIE_SECURE=false для локального HTTP, true для будущего HTTPS за прокси. Значение задаётся явно, а не определяется по недоверенному X-Forwarded-Proto. Некорректная конфигурация останавливает запуск с понятным сообщением. Загрузка .env отдельной библиотекой не нужна; README покажет переменные окружения.

## Сессии и защита запросов

При регистрации и каждом успешном входе создавать новый 32-байтный случайный токен; старую сессию этого браузера отзывать. Cookie session: HttpOnly, SameSite=Lax, Path=/, без Domain, Secure согласно конфигурации. Предлагаемый срок — 24 часа, абсолютный, без автоматического продления; срок в cookie соответствует сроку в БД.

При каждом запросе кабинета сервер проверяет хеш токена и expires_at и загружает пользователя из БД. Поддельная, удалённая или просроченная сессия не авторизует. Logout удаляет серверную сессию и cookie; повторное предъявление старого токена не работает. Просроченные записи очищаем при запуске и создании новой сессии. Ошибка БД возвращает 500, а не успешный гостевой ответ.

CrossOriginProtection применяется к формам регистрации, входа и выхода без разрешённых чужих origins. Его модель рассчитана на современные браузеры: запросы без Origin и Sec-Fetch-Site разрешаются, поэтому это не защита от произвольных HTTP-клиентов. GET/HEAD ничего не меняют. Размер POST-тела ограничиваем 8 КиБ, SQL использует параметры. Ответы кабинета и авторизации получают Cache-Control: no-store. В логах нет паролей, cookie, токенов и содержимого форм.

## Маршруты

| Маршрут | Поведение |
| --- | --- |
| GET / | Существующая главная, переход в кабинет. |
| GET /account | Формы для гостя; логин, статус и выход для вошедшего. |
| POST /register | Проверка полей, создание аккаунта и сессии, 303 на /account. |
| POST /login | Проверка пароля, новая сессия, 303 на /account. |
| POST /logout | Отзыв текущей сессии, удаление cookie, 303 на /account; повторный выход безопасен. |
| GET /healthz | Существующий 200 ok как проверка HTTP-процесса. |

Ошибки ввода — 400, занятый логин — 409, неверные данные входа — 401, отклонённый cross-origin POST — 403, слишком большое тело — 413, внутренняя ошибка — 500. Формы показывают понятные сообщения. GET к POST-маршрутам — 405. Для уже вошедшего пользователя POST /login и /register не переключают аккаунт: сначала выход.

## Приёмка и проверки

- На пустой временной БД зарегистрировать alice, увидеть кабинет и начальный статус; проверить, что в БД хранится хеш, а не пароль.
- Выйти, убедиться в отзыве старого токена, войти снова. Неверный пароль и неизвестный логин не создают сессию.
- Повторная регистрация ALICE и параллельная регистрация одного логина не создают дублей.
- Перезапустить сервер с тем же DB_PATH: аккаунт, статус и действующая сессия сохраняются. В тесте проверить сохранение статуса, отличного от начального, чтобы обнаружить случайный сброс при запуске; публичного способа менять статус пока нет.
- Второй клиент с отдельной cookie jar видит только своего пользователя; поддельная и просроченная cookie не дают доступ.
- Проверить срок/атрибуты cookie, оба режима Secure, запрет cross-origin POST, разрешение same-origin формы, методы, ограничения тела и граничные значения полей, включая UTF-8 пароль длиннее 72 байт.
- Повторить вручную в браузере регистрацию → кабинет → выход → вход → перезапуск → кабинет. Тестировать на отдельной временной БД, не стирать пользовательские данные.
- Из app/: go test -race ./..., go vet ./..., go build -o bin/server ./cmd/server. Проверить gofmt, git diff --check, отсутствие секретов и посторонних изменений. Если CI отсутствует, явно указать это в PR.
