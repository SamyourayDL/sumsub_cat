# Sumsub · инструкции проекта

Цель — подготовить к собеседованию развёрнутое приложение, в котором пользователь регистрируется, проходит проверку через Sumsub WebSDK и видит сохранённый результат.

## Начало работы

Прочитай project/state.md. Сопоставь запрос пользователя с текущей задачей и соответствующим этапом [плана разработки](project/plan.md). Для архитектурного выбора открой project/decisions.md, для интеграции — project/sumsub.md. Затем изучи затронутые файлы и ближайшие тесты. Если память расходится с кодом или фактическим состоянием Sandbox, проверь расхождение и исправь запись. Если работаешь в чате без доступа к файлам, запроси актуальный state.md и только материалы по текущей задаче.

## Выполнение

Работай над одним проверяемым результатом за раз. При обсуждении дизайна явно отмечай предложения. При реализации согласованной функции проверь её через пользовательский сценарий или подходящий тест. Объясняй по-русски, сохраняя английские названия SDK, методов и событий.

Следуй правилам Git ниже. По мере появления реальных команд заноси их в README приложения.

Для демонстрации используй Sandbox и тестовые данные. Привязывай SDK-токен к пользователю из серверной сессии. Секреты держи в локальном окружении или секретах хостинга. Исключай ключи, документы и персональные данные из Git, логов и памяти проекта.

## Передача задачи

Когда изменился результат, блокер или следующий шаг, обнови project/state.md. Укажи, что проверено и как это воспроизвести. В project/decisions.md добавляй принятые решения с причиной. Подтверждённые детали провайдера сохраняй в project/sumsub.md со ссылкой и датой. Для обычного вопроса, который ничего в проекте не меняет, запись не нужна.

## Git и pull request

- Одна короткая ветка и один PR в main на законченный, отдельно проверяемый результат. Пункт плана может включать несколько таких результатов. Не создавай ветку на каждый файл, коммит, тест или исправление замечания: связанные код, тесты, README и project/state.md входят в один PR.
- По умолчанию веди одну активную рабочую ветку. Заверши её PR перед следующим независимым результатом. Не вводи develop и цепочки зависимых PR без реальной необходимости. Например, HTTP-каркас с тремя маршрутами и проверкой — один PR.
- До изменений проверь status, текущую ветку, remote и незавершённый PR. Не включай чужие изменения в свой коммит. Для новой задачи обнови origin/main через fetch и создай от него ветку feat/<topic>, fix/<topic>, chore/<topic> или docs/<topic>. Существующую ветку той же задачи продолжай. Прямые коммиты и push в main больше не используй, включая служебные изменения.
- Делай осмысленные коммиты по ходу работы без искусственного дробления. Перед коммитом проверь diff, отсутствие секретов и git diff --check. Добавляй в индекс только относящиеся к задаче файлы.
- Пользователь разрешил автоматически создавать ветки, коммитить, отправлять рабочие ветки в origin, создавать и обновлять PR в main и выполнять squash merge после проверок в рамках порученной задачи. Повторное подтверждение этих действий не требуется. Это не разрешение расширять задачу, обходить защиту ветки или развёртывать приложение.
- В PR кратко опиши проблему, итоговое изменение и фактически выполненную проверку с командами и результатом. Укажи ограничения. Если работа ещё не готова, оставь PR в draft. Используй доступный GitHub-плагин; если его возможностей недостаточно — авторизованный gh CLI.
- Перед merge самостоятельно просмотри полный diff, проверь критерий результата и подходящие тесты или пользовательский сценарий. Для изменений только документации достаточно проверки diff, ссылок и согласованности инструкций; не запускай несуществующие тесты. Если CI настроен, дождись успешных обязательных проверок последней версии PR; ожидающие и упавшие проверки не считай успехом. Убедись, что нет конфликтов и нерешённых существенных замечаний. После изменения кода или базы слияния повтори затронутые проверки. Не обходи обязательное ревью или правила GitHub. Если CI отсутствует, явно укажи это и опирайся на выполненные локальные проверки.
- После squash merge проверь на GitHub, что PR действительно merged, синхронизируй локальный main через fast-forward и удали только завершённую рабочую ветку локально и в origin. При squash коммиты имеют другие SHA: перед удалением проверь merged-состояние PR и отсутствие новых локальных изменений или коммитов вне PR. Незавершённые ветки не удаляй.
- Не применяй force push, reset --hard, clean -fd и переписывание опубликованной истории без отдельного основания и согласования. Если GitHub недоступен, сохрани работу в ветке, сообщи точный блокер и следующий шаг; не заменяй PR прямым merge в main.
- В итоговом ответе дай ссылку на PR, статус merge и краткий результат проверок. Правила действуют для этого проекта; глобальные Git-настройки не меняй.
