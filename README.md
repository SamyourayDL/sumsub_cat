# Sumsub demo

Учебное приложение для регистрации, проверки пользователя через Sumsub WebSDK
и сохранения результата. Интеграция будет использовать Sandbox.

## Локальный запуск

Готовы этапы 1–3: регистрация, вход, выход, кабинет и мем для пользователя
со статусом `approved`. Пользователи и серверные сессии хранятся в SQLite.
Sumsub пока не подключён; одобрение проверяется только на локальных тестовых данных.

Требуется Go 1.27.4. При установленном Go 1.21+ и стандартном
`GOTOOLCHAIN=auto` нужная версия загрузится автоматически при первом запуске
(нужен интернет). При отключённой автозагрузке установите Go 1.27.4 вручную.
Версия закреплена в `app/go.mod`; для будущей контейнерной сборки используем
ту же версию Go. Зависимости modernc.org/sqlite и golang.org/x/crypto
загрузятся автоматически; CGo и секреты не нужны.

Из корня проекта:

```sh
cd app
go run ./cmd/server
```

Откройте [главную](http://localhost:8080/) и перейдите по кнопке
в [личный кабинет](http://localhost:8080/account).
Остановить сервер — `Ctrl+C`. Порт 8080 должен быть свободен.
Сервер слушает `:8080` на всех интерфейсах, включая локальную сеть.

В другом терминале:

```sh
curl -i http://localhost:8080/healthz
```

Ожидаемый ответ — HTTP 200, `Content-Type: text/plain; charset=utf-8`
и тело `ok`. Неизвестные пути возвращают 404; GET к маршрутам
`/register`, `/login`, `/logout` возвращает 405 — изменения выполняются через POST.

## Конфигурация и ручная проверка

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DB_PATH` | `data/app.db` | Путь к файлу SQLite относительно рабочего каталога. Каталог и схема создаются автоматически. |
| `MEME_PATH` | `resources/meme.jpg` | Отдельный JPEG или PNG относительно рабочего каталога; читается при каждом разрешённом запросе. |
| `COOKIE_SECURE` | `false` | `false` для локального HTTP; `true` для будущего HTTPS, в том числе за прокси. |

Пример из каталога `app/`:

```sh
DB_PATH=data/local-check.db COOKIE_SECURE=false go run ./cmd/server
```

`.env` автоматически не читается. Неверная конфигурация или более новая неизвестная
версия схемы останавливает запуск. Новый каталог БД создаётся с правами 0700,
файл — 0600; права существующих путей не меняются. Не используйте реальные
учётные данные: это учебное приложение.

1. Откройте `/account`: сначала отображается вход. Нажмите «Зарегистрироваться»,
   чтобы открыть `/account/register`. Зарегистрируйте вымышленный логин `demo_alice` и свой
   тестовый пароль: минимум 12 символов, максимум 72 байта UTF-8.
2. Убедитесь, что в кабинете указан ваш логин и «Проверка не начата».
3. Нажмите «Выйти». Перейдите к регистрации и попробуйте логин `DEMO_ALICE`: получите сообщение
   «Этот логин уже занят». Войдите в прежний аккаунт; регистр логина не важен.
4. Не выходя из аккаунта, остановите сервер (`Ctrl+C`), запустите той же командой
   и обновите кабинет: сессия и статус должны сохраниться.
5. В приватном окне зарегистрируйте другой логин: окна должны показывать разные аккаунты.
6. Проверьте неверный пароль: сообщение «Неверный логин или пароль», без входа.

Сессия действует 24 часа с момента входа без продления. Выход немедленно отзывает
текущую сессию; сессии в других браузерах остаются действующими. Пароли хранятся
как bcrypt-хеши с cost 12, токены сессий — только как SHA-256-хеши. Cookie имеет
HttpOnly и SameSite=Lax. Формы защищены `http.CrossOriginProtection`; запросы без
Origin и Sec-Fetch-Site эта защита допускает — это не ограничитель HTTP-клиентов.

До публичного деплоя нужно добавить защиту входа от перебора и ограничения нагрузки
(включая дорогие bcrypt-операции), включить Secure cookie и настроить HTTPS.
Проверка Sumsub и смена статуса в интерфейсе относятся к следующим этапам.

## Проверка доступа к котику

Используйте отдельную тестовую базу. Из каталога `app/`:

```sh
DB_PATH=data/meme-check.db COOKIE_SECURE=false go run ./cmd/server
```

1. Откройте [главную](http://localhost:8080/): гость видит прежнюю карточку.
   Прямой [адрес мема](http://localhost:8080/meme) возвращает 401.
2. Зарегистрируйте `cat_alice`. Главная пока не меняется, `/meme` возвращает 403.
3. В другом терминале из `app/` задайте тестовое одобрение:

   ```sh
   sqlite3 data/meme-check.db "UPDATE users SET verification_status='approved' WHERE login='cat_alice'; SELECT login, verification_status FROM users WHERE login='cat_alice';"
   ```

   Ожидается `cat_alice|approved`. Обновите главную: вместо карточки — ваш котик
   с мечом целиком, справа сверху — «Личный кабинет». В кабинете пока отображается
   технический статус `approved`.
4. В приватном окне зарегистрируйте `cat_bob`: ему `/meme` по-прежнему возвращает 403.
5. В первом окне выйдите через кабинет: прямой URL возвращает 401. Войдите снова —
   мем доступен. Перезапуск сервера с той же DB_PATH также сохраняет результат.
6. Отзовите одобрение и обновите главную и прямой URL:

   ```sh
   sqlite3 data/meme-check.db "UPDATE users SET verification_status='not_started' WHERE login='cat_alice';"
   ```

   Возвращается карточка, `/meme` — 403. Изменение действует на следующий запрос,
   уже показанное или скачанное изображение не удаляется.

SQL предназначен только для этой локальной тестовой БД. Публичного маршрута
смены статуса нет; после интеграции статус будет устанавливать backend по результату Sumsub.
Не меняйте таким способом рабочие пользовательские данные.

GET и HEAD `/meme` проверяют текущую сессию и свежий статус в SQLite.
Любой статус кроме точного `approved` закрывает доступ. Гость, истёкшая или отозванная
сессия получают 401, неодобренный пользователь — 403, ошибка БД — 500.
После проверки доступа отсутствие файла даёт 404; нечитаемый файл, каталог или
неподдерживаемый тип — 500 без раскрытия пути. Поддержка формата определяется
по сигнатуре содержимого, а не расширению; полная проверка целостности изображения
не выполняется. `/resources/meme.jpg` через HTTP не опубликован.
Главная и `/meme` получают `Cache-Control: private, no-store`; изображение — `nosniff`.

## Замена картинки

Предоставленный тестовый мем перемещён в `app/resources/meme.jpg` и хранится в Git.
Для своей локальной картинки используйте игнорируемый `app/data/` и `MEME_PATH`:

```sh
DB_PATH=data/meme-check.db MEME_PATH=data/my-cat.png go run ./cmd/server
```

Положите JPEG или PNG по указанному пути перед запросом. Для замены работающего
ресурса сначала скопируйте новый файл во временное имя в том же каталоге,
затем переименуйте поверх старого (пример из `app/`):

```sh
cp /absolute/path/new-cat.jpg data/my-cat.next
mv data/my-cat.next data/my-cat.png
```

Обновление страницы сразу получает новые байты — сборка и перезапуск не нужны.
Расширение может оставаться прежним: HTTP Content-Type определяется по содержимому.
Изменение самой переменной MEME_PATH требует перезапуска сервера.
Файл не встроен в бинарник; при переносе приложения его нужно переносить отдельно.

## Проверки и сборка

Из каталога `app/`:

```sh
go test -race ./...
go vet ./...
go build -o bin/server ./cmd/server
./bin/server
```

Шаблоны HTML встроены через `go:embed`: собранный бинарник можно запускать
из любого каталога без копирования HTML рядом. Относительные DB_PATH и MEME_PATH
считаются от рабочего каталога; при запуске из другого каталога задавайте абсолютные пути.
Тесты используют временные файловые базы и проверяют регистрацию, повторный вход,
отзыв и срок сессий, изоляцию клиентов, конкурентную регистрацию, атомарность,
сохранение изменённого статуса после открытия БД, CSRF, cookie, лимиты и ошибки БД.
Тесты мема дополнительно проверяют GET/HEAD, доступ разных пользователей, отзыв статуса,
замену JPEG на PNG без перезапуска, отсутствие публичной статики и ошибки файла.
В браузере проверены прежняя главная, одобренный пользователь, широкий и узкий
экран (390×844), переход в кабинет и отказ после выхода.
CI пока не настроен; эти проверки запускаются локально.

## Работа над проектом

Один проверяемый результат — одна короткая ветка и один PR в `main`.
Связанные код, тесты и документация входят в один PR. После проверок ассистент
автоматически выполняет squash merge и удаляет завершённую ветку.
Подробные правила — в [AGENTS.md](AGENTS.md#git-и-pull-request).

Для локальных изменений используется Git, для PR — GitHub-плагин или
авторизованный GitHub CLI (`gh`). SSH-доступ для push сам по себе не даёт
CLI авторизацию к API для управления PR.

Локальные настройки этого репозитория (повторить после нового clone):

```sh
git config --local pull.ff only
git config --local fetch.prune true
git config --local push.default simple
```

`pull` допускает только fast-forward; `fetch` удаляет устаревшие ссылки
на удалённые ветки; `push` по умолчанию отправляет текущую ветку с совпадающим
именем upstream. Это удобные настройки, а не защита `main` на стороне GitHub.

При работе из `app/` локальные секреты храните в `.env` или каталоге `secrets/`, локальные данные
и документы — в `data/` и `uploads/`. Эти пути, файлы SQLite и логи
исключены из Git. Не добавляйте реальные документы и персональные данные
в исходники, проектные заметки или коммиты.
